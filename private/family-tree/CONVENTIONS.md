# Конвенции кода

Обязательны для всего проекта. При разработке и ревью сначала сверяться с этим файлом.

## 1. Архитектурные принципы

### 1.1. Атомарность и ответственность

- Один файл содержит одну основную сущность: компонент, хук, store, публичную функцию или доменный тип.
- Несвязанные экспортируемые сущности нельзя складывать в один файл «для удобства».
- Маленькие приватные helper-функции разрешены рядом с основной сущностью, если они используются только в этом файле и остаются короткими.
- Если helper нужен в двух местах или заметно усложняет файл — вынести его в отдельный файл.
- Компонент отвечает за отображение и связывание событий; доменная логика и изменения состояния находятся в hook/store/lib.

### 1.2. Простота и явность

- Не добавлять абстракции, generic-обёртки и паттерны без конкретной текущей потребности.
- Прямое и очевидное решение предпочтительнее гибкого решения «на будущее».
- Не скрывать важное поведение за неявными дефолтами и магией.
- Не глотать ошибки. Некорректный результат должен явно возвращаться как `null`/`undefined` либо приводить к понятной ошибке.

### 1.3. Кастомный UI

- Карточки, меню, модалки, кнопки и поля ввода — отдельные именованные компоненты в `src/components/`.
- UI-библиотеки используются только как примитивы. Поверх примитива создаётся тонкий компонент с логикой проекта.
- Стили компонента хранятся рядом с компонентом в отдельном `.css`, если компоненту нужны собственные стили.

## 2. Именование и экспорты

- Компоненты: `PascalCase.tsx` (`PersonCard.tsx`).
- Хуки, функции и файлы логики: `camelCase.ts` (`useClickOutside.ts`, `calculateAge.ts`).
- Стили компонента: имя компонента + `.css` (`PersonCard.css`).
- Доменные типы: `camelCase.ts` в `src/types/` (`person.ts`, `canvasViewport.ts`).
- Store-файлы: `use<Domain>Store.ts` (`useCanvasCardsStore.ts`).
- Использовать только именованные экспорты. `default export` запрещён для исходников приложения.
- Props и локальные типы компонента объявляются в файле компонента.
- В `src/types/` выносятся только общие доменные типы, используемые в нескольких модулях.

Исключение: конфигурационные файлы инструментов могут использовать требуемый инструментом формат экспорта.

## 3. Импорты и публичный API

- В исходниках использовать абсолютные импорты через алиас `@/`.
- Не использовать длинные относительные пути и не импортировать соседние файлы через `./`.
- `index.ts` разрешён как явный barrel-файл для папки с несколькими публичными сущностями, но не добавляется автоматически во все директории.
- Не оставлять неиспользуемые компоненты, типы, стили и импорты.
- Циклические зависимости между компонентами, store и lib не допускаются.

## 4. Состояние и данные

- Один store — одна доменная область.
- Файл store содержит состояние и атомарные actions этой области.
- UI не изменяет состояние напрямую в обход store или специализированного hook.
- Доменная модель не должна зависеть от React-компонентов или CSS.
- Поля, которые могут отсутствовать, моделируются как optional и не рендерятся без значения.

## 5. Доступность и стандартное поведение

- Интерактивные элементы должны быть настоящими `<button>`, `<input>` и другими семантическими HTML-элементами.
- Для иконок-кнопок обязательны `aria-label` и, если нужно, `title`.
- Меню и модалки закрываются по клику вне области и по `Escape`.
- Клавиатурная навигация должна работать через `Tab`, `Enter`, `Space` и стандартные клавиши компонента.
- Фокус должен быть видимым через `:focus-visible`.
- Не отключать `outline` без равноценного видимого состояния фокуса.

### 5.1. Геометрия связей

- Линия связи никогда не должна проходить через карточку человека. Точки начала и конца вычисляются от ближайших сторон карточек, каждый сегмент проверяется на пересечение с прямоугольниками карточек, а при конфликте строится безопасный ортогональный обход.
- Проверка выполняется для обоих сегментов связи и для всех карточек, включая карточки, не являющиеся участниками этой связи.
- Любая линия связи начинается и заканчивается с зазором 10 px от границы объекта: карточки, фото-круга, сердечка или хаба. Линия не касается объекта вплотную.
- Линии разных связей никогда не могут совпадать и идти одним маршрутом или одним вертикальным/горизонтальным сегментом. Если перемещение хаба приводит к совпадению с другой линией, хаб автоматически возвращается на последнюю безопасную высоту.
- Интерактивная линия связи должна открывать редактор соответствующей связи по клику.
- Визуализатор брака принимает и рисует только связи с типом `marriage`; связи `parenthood` и любые будущие типы не должны попадать в брачный слой.
- При чтении старых данных запись с `union_type='marriage'` и ролью `father`/`mother` нормализуется в `parenthood`, чтобы исторические родительские связи не отображались как брак.
- Фото пары принадлежит записи брака: путь хранится в `details_json`, файл хранится вне SQLite в каталоге медиа, а контекстное редактирование не меняет геометрию связи.

### 5.2. Геометрия поколений

- Внутреннее поле поколения составляет 40 px сверху и 40 px снизу.
- Один родительский хаб — это брачная пара, у которой есть связь с ребёнком; пары без детей в расчёт не входят.
- Между соседними родительскими хабами учитывается 20 px по вертикали.
- Карточки поколения центрируются по высоте между его защитными линиями; защитные линии находятся на 40 px выше верхней и ниже нижней границы карточек.
- Просвет между нижней защитной линией одного поколения и верхней линией следующего равен `40 + 40 px + 20 px × (количество хабов − 1)`; при нуле хабов используется базовый просвет 40+40.
- Высота поколения рассчитывается как высота карточки плюс два защитных отступа по 40 px и этот межлинейный просвет.
- Все карточки во всех поколениях перемещаются по одинаковым правилам: обычное перетаскивание свободно меняет X и Y, действующие супруги перемещаются вместе, а `Alt` временно отделяет выбранную карточку от супруга. Поколение карточки не меняет правила перемещения.
- После обычного отпускания сохраняются фактические мировые координаты и выполняется автоцентрирование родительских групп; перемещение через `Alt` сохраняет отдельную пользовательскую позицию без возврата.

### 5.3. Единый контракт размещения карточек

- `card.x` — левая граница карточки в мировых координатах.
- `card.y` — геометрический центр карточки по вертикали, а не её верхняя граница.
- Карточка всегда имеет размер `250×350 px`; расчёты размещения не используют захардкоженные альтернативные размеры.
- Номер поколения вычисляется только через единый `getGenerationHeight()`; запрещены отдельные значения высоты поколения в store, Rust, импорте и компонентах.
- Координата поколения задаётся центром поколения: карточка располагается строго посередине защитной зоны, а не у одной из её границ.
- Брачная пара является одной группой только для перемещения: муж слева, жена справа, расстояние между карточками хранится в данных брака.
- Родительская связь никогда не делает карточки группой супругов и не использует брачную геометрию.
- После создания или изменения родительской связи и после обычного перемещения карточек выполняется автоцентрирование соответствующей родительской группы; `Alt` отключает это выравнивание только для текущего отдельного перемещения.
- При двух родителях целевой X — центр карточек родителей, если между ними есть брак; при одном родителе — центр его карточки.
- Если у родителей есть общие дети, группой выравнивания являются все эти дети и их брачные партнёры; группа перемещается целиком с сохранением относительных расстояний.
- Кнопка выравнивания рассчитывает положение заново по этим правилам и не меняет данные связей.
- Команда «Центрировать всё дерево» вычисляет bounds-центр всех карточек и применяет один общий `dx/dy`; она не перестраивает карточки, не меняет расстояния и сохраняет взаимное расположение.
- Любое перемещение сначала меняет локальное состояние, затем сохраняется в SQLite теми же мировыми координатами; после сохранения `load_cards` не должен возвращать другое положение.
- Перед отрисовкой любой линии выполняется проверка пересечения каждого сегмента со всеми карточками. При пересечении линия не рисуется.
- Визуальный слой брака фильтрует только `marriage`; родительские записи не могут попасть в него даже при ошибочном порядке или старом формате данных.
- Брачные связи визуализируются во всех поколениях и не ограничиваются номером поколения или положением по вертикали.
- Центр детского хаба считается только между центрами самой левой и самой правой карточки детей данной родительской группы; супруги детей и другие выходящие связи не расширяют хаб.
- Родительские хабы занимают общую вертикальную высоту, если их линии не пересекаются по горизонтали. При появлении конфликта хаб получает отдельную вертикальную дорожку в межпоколенческом промежутке; при необходимости межпоколенческое пространство увеличивается на высоту/шаг хаба.
- Высоту положения хаба можно менять мышью. Используемую высоту занимать можно, но нельзя совпадать с уже используемым маршрутом линии на этой высоте; при конфликте хаб возвращается на предыдущее безопасное положение.

### 5.4. Каноническая схема детских линий и хабов

Этот раздел является единственным правилом для визуализации связей `parenthood`; альтернативные схемы, специальные ветки для отдельных поколений и отдельные правила для одиночных случаев не допускаются.

- Родительская линия синяя и имеет ту же толщину, что и брачная линия. Брачная линия красная; различается только цвет и тип связи.
- Линия от ребёнка начинается в центре верхней стороны карточки и заканчивается с зазором 10 px до хаба.
- При одном ребёнке горизонтальный хаб не рисуется: вертикальная линия идёт непосредственно к центру хаба.
- При нескольких детях хаб проходит от центра крайней левой карточки ребёнка до центра крайней правой карточки ребёнка. Его центр находится между этими крайними карточками.
- Супруги детей и связи, выходящие за пределы крайних карточек детей, не расширяют детский хаб.
- При двух родителях линия от родительской пары начинается в центре фактически отображаемого сердечка брака, с зазором 10 px, и идёт к центру детского хаба.
- При одном родителе линия начинается в центре нижней стороны карточки известного родителя, с зазором 10 px, и идёт к детскому хабу.
- Родительская линия не является брачной: она не использует сердечко брака как собственный маркер, не объединяет родителей в группу перемещения и не меняет статус брака.
- Для разных наборов родителей создаются разные группы и разные хабы. Связи разных родительских групп не объединяются.
- Межпоколенческая область существует всегда. Хабы размещаются только внутри неё, не в защитной области карточек.
- При включённой автоцентровке первый хаб и группа автоматических хабов центрируются в свободной межпоколенческой области. Автоматические хабы используют одну высоту, если их маршруты не конфликтуют.
- При отключённой автоцентровке хабы занимают отдельные дорожки от верхней границы межпоколенческой области с шагом 20 px. Последний добавленный хаб находится ближе к верхней границе.
- При совпадении маршрутов автоматических хабов показывается предупреждение. После подтверждения создаётся отдельная дорожка с шагом 20 px; линии не могут использовать один и тот же вертикальный или горизонтальный участок.
- Родительские маршруты не обходят карточки и не используют маршрутизатор препятствий. Вертикали родителей и детей и горизонталь хаба строятся только внутри межпоколенческой области; единственное допустимое пересечение — пересечение неавтоцентрированного хаба с вертикалью родительской связи.
- Обходы родительских линий, полукруги и дополнительные маршруты запрещены. При конфликте высоты меняется дорожка хаба по правилам автоцентровки или ручного шага 20 px.
- Перед отрисовкой проверяется каждый сегмент каждой родительской линии относительно всех карточек, включая карточки участников связи. Точка подключения уже находится за пределами объекта на 10 px.
- Одинарный клик по родительской линии только выделяет её, двойной клик открывает редактор, ПКМ открывает меню редактирования и удаления.

## 6. Проверки перед завершением задачи

Перед передачей результата выполнить:

```bash
pnpm build
git diff --check
```

Дополнительно проверить:

- `git status` — в рабочей директории нет неожиданных файлов;
- нет остатков удалённых компонентов и stale-импортов;
- поведение, затронутое изменением, проверено в интерфейсе;
- `README.md` и `DEVLOG.md` обновляются только по прямой команде пользователя.

## 6.1. Целостность данных и файлы

- Любая операция, изменяющая несколько таблиц, выполняется одной SQLite-транзакцией.
- Перенос рабочего каталога сначала готовится в staging-копии; старый каталог удаляется только после успешной проверки базы, обновления ссылок и атомарной записи конфигурации.
- Ошибка записи медиа не оставляет запись в SQLite и не оставляет временный файл на диске.
- Удаление из корзины сначала фиксируется в базе, затем удаляет файлы медиа; ошибка удаления файла не должна приводить к удалению чужого каталога.
- Конфигурация и экспорт записываются через временный файл с безопасным переключением; исходный файл сохраняется до успешной замены.
- JSON-экспорт является полным снимком текущей модели: люди, мировые координаты, дополнительные поля и связи. При импорте все системные ID назначаются заново, а связи получают новые ID участников.
- Новые форматы и схема проектируются как целевой контракт проекта; переходные ветки совместимости не добавляются без отдельной команды пользователя.
- Пути, переданные в файловые операции, проверяются до записи и удаления; имя дерева не может содержать разделители, управляющие или зарезервированные имена Windows.

## 7. Git и коммиты

- Коммиты создавать только по прямому указанию пользователя.
- Без такого указания можно проверять `git status`, `git diff` и историю, но нельзя выполнять `git commit`.
- Сообщение коммита должно кратко описывать завершённое изменение.
